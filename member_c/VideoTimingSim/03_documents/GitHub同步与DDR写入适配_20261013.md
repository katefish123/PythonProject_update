## 本次新增模块

`01_design_code/ddr_block_writer.v` 接收 `rgb888_block_packer` 的 256 位块流，输出 A `ddr_word_engine` 的单命令/单应答写口。全部信号同一时钟，不承担跨时钟转换。

- `frame_start && frame_start_ready` 开始帧，锁存 `frame_base_byte`。基址必须 32 字节对齐且小于 1 GiB；错误基址返回一次 `frame_done=1, frame_ok=0`，不会发 DDR 命令。
- `block_valid && block_ready` 接收一个块，保存数据、字节掩码及 `block_last`。等待期间不接收下一块，命令和负载保持稳定。
- A 地址单位是 32 位字；本模块转换 `cmd_addr=frame_base_byte>>2`，每块增加 8 个字。`cmd_write` 固定为 1。
- 最后一块得到写应答后，才产生一次 `frame_done`；成功时同拍 `frame_ok=1`。不能仅根据 `block_last` 发布帧。
- `frame_abort` 在命令尚未接受时取消该命令；与命令接受同拍时视为已经发出，必须等待应答。已经接受的写事务没有撤销手段。
- `mem_fault` 或错误的 `rsp_write` 作废本帧。待应答期间即使发生错误/取消，也保持 busy 直到应答回来。故障状态恢复必须与 DDR 引擎共同复位并清空事务。
- 下一块将越过地址范围时作废本帧，不允许地址回绕。最后一块恰好结束在范围末尾允许成功。

这个模块只证明块写入完成，不检查源图行宽、总像素数或迟到的输入错误。调用者必须同时确认源帧完整、没有输入溢出/`frame_abort`，才可发布 `ddr_frame_slots` 的最新帧。如果 writer 的 `frame_done && !frame_ok`，需要同拍给 slots 的 `capture_abort=1` 与 `write_complete=1`，释放该槽但不发布；失败时也要丢弃 packer 尚未发出的块。在 `frame_done` 之后才发现源帧错误，则不能直接发布，须由采集事务管理统一确认源结束及写结束。

槽授权到来前保留首像素；writer 开始接收前先等待 `frame_start` 握手。此阶段未新增事务管理顶层，因此没有把这些组件直接接入原 HDMI 实测顶层。

## 地址分区：上板前必须统一

A 当前源区从字地址 0 开始，结果区默认 `BASE0=0x0100000`、`BASE1=0x0200000`，即字节地址 `0x00400000`、`0x00800000`。我们计划的一个 1920×1080 RGB32 源帧为 8,294,400 字节；三槽连续布局会覆盖 A 目前的结果区。

因此本次仿真中的三槽基址只是地址换算验证，不能直接用于 A 现有完整工程。后续统一源三槽、结果双槽、缓存范围以及所有写入/四邻域读/显示读模块的基址参数，再进行整机回归。A 连续预读版的 `RESULT_BASE0/1` 与 `RESULT_WORDS` 也必须同步更新。不要仅改写端地址。

## 接续顺序

1. 统一内存分区，并参数化 A 源缓存/结果写入/结果显示/预读范围。
2. 接入源事务管理和有容量检查的 RX→UI FIFO：相机无法因 DDR 等待而停止出像素，FIFO 溢出必须作废整帧并等待写事务排空。

4. 基于锁定的源槽给 B 返回四邻域数据和原请求元数据；无 ready 接口需要在目的像素发起端限制并发量。
5. 完整集成仿真及 PDS 时序通过后，保留基础版回退，再做真实 DDR/相机验收。
