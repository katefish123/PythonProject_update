# 新常显诊断/修复候选上板：一次取证方案

由烧录窗口独占设备。只有本候选最终资格及package check-only通过后执行CRAM Program/Verify，不写Flash。以包与日志中的完整bit SHA为准，不用日期/文件名代替。

烧录并按既定一次KEY0基线后，不反复切RAW或双键；新版本HUD常显。待HDMI/DDR就绪，直接保存两张相隔约3秒的原生1920×1080无遮挡采集源PNG，并保留单调时间戳和全20位×24行数据。

先看row17高32位扫描计数：若增加约180，证明所见HUD随板上像素扫描推进；不是以OBS渲染FPS作为源更新证明。若扫描不变，先查观测链路和板时钟/复位。计数只在scan_reset_n有效时推进，普通应用复位不会被误计为大量扫描。

再看row01物理输入、接纳，row02丢弃/拒收，row03 RAW/校正发布及row00实际PIX模式、银行、基址、ID。不以KEY1是否按过代替实际模式。默认CORRECTED仍应有新发布且实景运动；用户接受低于60张新图/秒，但必须报告真实发布率、显示更新及延迟，不能用60Hz扫描代替。

拒帧定位：row06高/低32位为原因12/13，row07为14/15。原因12指输入不完整，13指RX溢出，14为协议/代际或处理路径错误，15为写入不完整等；总计数混合source与processor相同原因编号，需结合发生阶段，不将编号独断归给单模块。若13持续增、FIFO满且发布停住，再结合服务计数和等待分布判断capture吞吐。若12增则核RX完整性/分辨率/时序，不把它改名overflow。错误14/15需要逐模块记录再查。

row16 bit79为独立欠载历史锁存观察；与current_mask分开报告，记录复位基线。row12 AW/AR次数和row13累计等待只反映全局服务压力；增量等待/增量命令可给区间均值估计，但跨区间边界、恢复/计数回绕以及多客户混合都需注明，不冒称某一客户真实延迟。

如果修复候选仍停更或欠载，保留两图、完整HUD、Program/Verify日志及变化时间，再把明确原因返给开发；不重复烧相同文件、不盲换相机参数。白灰/停更暂消失后，才继续15秒运动、RAW/校正对照、真实新图率与延迟、10分钟及重连验收。正式标定/光学指标和未集成纸框功能仍另列，不被本轮链路修复自动完成。
