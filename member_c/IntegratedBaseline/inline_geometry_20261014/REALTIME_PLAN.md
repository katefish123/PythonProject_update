# 连续视频目标与下一阶段实现约束

2026-10-15，用户在烧录聊天明确选择“连续视频流畅，画面实时跟随”，并授权将要求发送到本开发聊天。本轮采集内检测仅是一项基础优化，约数百毫秒的更新间隔不满足连续视频目标。

保留原每秒60张不同完整校正图的最终目标。烧录聊天提出“至少30张/秒、端到端延迟不超过100ms”作为拟定中间工程门槛，这个数字尚不是用户单独确认的降档要求，更不是已测实机性能。输入完整1920×1080，结果640×904，比例不变。

## 容量与带宽

每张结果578,560像素，60次/秒需34,713,600结果像素/秒。当前27MHz单像素通道即使每拍都出结果，理论下界21.43ms，无法达到16.67ms。增加队列不能改变这个上限。

当前原生接口256位、125MHz，理想峰值4GB/s。以下按32位存储一个RGB像素、60次/秒计算有效像素载荷；四邻域行按每像素四次请求计算。它不是实际DDR总线流量估计，尚未计缓存复用、突发多读、命令开销、行切换与刷新：

| 流量 | 理想值 |
| --- | ---: |
| 完整输入写入 | 497.664MB/s |
| 结果写入 | 138.8544MB/s |
| HDMI结果读取 | 138.8544MB/s |
| 四邻域请求的有效像素载荷 | 555.4176MB/s |
| 合计 | 1330.7904MB/s |

若四次邻域请求分别miss，每次最少读取一个32字节原生拍，其物理读流量可达4.4433408GB/s；再加输入、结果写和显示读取的约0.775GB/s，已超过4GB/s理想接口峰值。若误用更大突发还会进一步放大。必须测量四邻域去重、块复用、实际读写拍数、突发利用率、命令首拍开销、等待周期和缓存命中率，不能由有效像素载荷宣称带宽足够。

## 实施顺序

1. 先做带银行和帧代次的块缓存/邻域收集器。一次获取四邻域，不再让同一像素的四次读取贯穿整个处理状态机。失效必须覆盖源银行被重新采集、abort、复位，以及未完成填充；不能只用银行号识别新旧帧。
2. 用信用额度和标签队列解耦坐标、邻域、原 B 插值、结果写入。坐标通道先预留实际容量再发出，完成帧必须等待全部标签按序排空及DDR写入完成。慢端背压不得覆盖仍在流水线中的数据。
3. 比较两种硬件组织：单通道提高处理时钟，或两条原27MHz像素通道配合UI域邻域收集。原B除法和插值都支持每拍输入，当前C状态机没有用上其吞吐。单通道需验证宽算术高频时序；双通道需验证标签合并、资源和跨域队列。不能未经综合/模型测量就认定其中一种能达标。
4. 采集端需要提前准备下一个源缓冲。现有快照在下一VS才完成，不支持同边沿接入新请求，存在空帧机会。改成连续采集后还需明确“正在写、完整可读、正在处理”所有权，并统计主动丢帧，禁止覆盖处理中的源图。

现有采集协议在60Hz源上即使处理无限快也约每两帧才能取一帧，上限约30个不同源帧/秒，达成60必须改协议。单通道108MHz若仍串行四读、每像素至少四拍，上限也仅27M像素/秒；双通道27MHz要达到目标，平均每通道仅约1.56拍/结果像素，仍不能保留当前等待状态机。

## 已完成的下一阶段访问轨迹测量

[trace_gather.py](trace_gather.py) 重放三张完整结果的全部四邻域地址，坐标由当前B定点系数生成，并和B标量函数抽检一致。每帧578,560个输出、2,314,240次像素读取。以下是不同候选缓存的**假设填充字节**，不是周期仿真或实机吞吐：

| 缓存组织 | 图0 | 图1 | 图2 |
| --- | ---: | ---: | ---: |
| 原2条8像素LRU | 13,397,728 | 13,326,464 | 13,286,752 |
| 128组×2路，8像素块 | 7,256,992 | 6,972,544 | 6,891,968 |
| 128组×2路，64像素长条 | 3,742,464 | 6,141,184 | 8,942,336 |
| 64个64×4像素块，全相联FIFO | 3,492,864 | 3,457,024 | 3,424,256 |

后两种都假设64KiB数据容量。长条策略随倾斜变化明显，第三图反而比8像素策略读取更多；64×4的空间块较稳定。FIFO策略在本组三图中与完全LRU接近，可避免大LRU更新网络。原生256位接口中，一个64×4块需要四个8拍行突发；三帧假设行突发命令分别13,644、13,504、13,376次。此结果支持先做空间块gather原型，但尚未验证BRAM端口冲突、关联比较时序、仲裁、真实UI缓存命中、流水线背压或实际DDR开销；不能换算为已达到的帧率。完整记录见 [gather_trace.json](gather_trace.json)。

下一件实现工作据此收敛为：UI域64×4空间块、64条全相联FIFO替换的邻域收集器，先验证实际RAM端口和四次行突发填充；用真实坐标轨迹验证全输出像素、停顿及物理命令量，再决定单通道升频还是双27MHz通道。两读口若每个结果至少用两拍，125MHz理想上限62.5M结果/秒，但这仅是全命中容量上限，必须扣除填充、关联查找、背压和仲裁开销。不能把该上限当成目标已实现。

烧录聊天当前保留的 `540dd628` 原子8拍采集突发修正是另一条本地已烧录基线。本候选尚未合入该补丁；今后合并必须同时适配两个源缓冲范围、银行包装器、完整突发旁路载荷及源缓存失效，不可只照搬其单源 `cmd_addr<SOURCE_WORDS` 判定。该基线与本轮黑标三帧模型配置不同，不能直接比较数值或继承29项回归/板测资格。

## 验收

完整模型必须使用内容、四角和单应矩阵都随帧变化的输入。统计输入帧编号、采集开始/完成、处理开始/完成、发布、显示首次可见的时间，以及丢帧原因；逐像素核对B参考，校验显示连续代次。三帧模型适合功能回归，持续吞吐验收还需更长的完整帧序列，不能只由首帧或两次间隔外推长期性能。

只有持续发布间隔、图像年龄、丢帧与最终PDS时序都符合门槛，才进入对应档位的板测。板测由“明确烧录专用需求”聊天统一执行；当前开发不下载、不覆盖板上程序。

相机目前拍摄同一电脑屏幕，打开OBS可能遮住目标。实际识别稳定性测试必须让目标持续可见；相机图像、校正结果和OBS界面叠加分别记录。清晰度要对比原始采集与校正结果，不能用放大预览代替画质改善。
